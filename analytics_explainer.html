Section 1
What Each Analytics Type Does

Rule-Based Analytics

Evaluates each application against a set of pre-configured eligibility rules using IF-THEN logic. Each rule defines a field to check, a condition, and a threshold value. The result is a deterministic classification — Pass or Flag — with a list of violated criteria.

IF-THEN evaluation Decision table Classification

Answers: "Does this applicant qualify based on the configured rules?"

Descriptive Analytics

Examines historical application records to answer the foundational question, "What happened?" It transforms raw application data into patterns and metrics using sums, averages, and percentages. It is the starting point for all other forms of data analysis.

Frequency counts Percentages Time-series grouping

Answers: "What happened over time? How many applied, were approved, or were flagged?"

Section 4
CS Algorithms Used
Algorithm A — Decision Table Evaluation
Rule-Based Analytics · programs/services.py
Time: O(r × a) 
// r = number of rules,  a = number of applications
FUNCTION run_rule_evaluation(application):
  reasons ← []
  rules   ← ProgramRule.objects.filter(program=application.program)

  FOR EACH rule IN rules:
    actual ← _get_actual_value(rule.rule_field, application)
    passed ← _evaluate_condition(rule.condition, actual, rule.value)
    IF NOT passed:
      reasons.append(rule.name)

  outcome ← "flag" IF reasons ELSE "pass"

  ScreeningResult.save(outcome=outcome, reasons=reasons)
  RETURN outcome

// Condition evaluation (simplified)
FUNCTION _evaluate_condition(condition, actual, threshold):
  MATCH condition:
    "lte"       → RETURN actual ≤ parse_number(threshold)
    "gte"       → RETURN actual ≥ parse_number(threshold)
    "equals"    → RETURN actual == threshold
    "in_list"   → RETURN actual IN threshold.split(",")
    "date_after"→ RETURN parse_date(actual) > parse_date(threshold)
Algorithm B — Hash Map Frequency Count
Descriptive Analytics · config/views.py (screening breakdown)
Time: O(n × k) 
// n = flagged results,  k = reasons per result,  d = distinct rules
// Space: O(d)
FUNCTION compute_rule_frequency():
  freq_map ← {} // hash map: rule_name → count

  flagged ← ScreeningResult.objects.filter(outcome="flag")

  FOR EACH result IN flagged:            // O(n)
    FOR EACH reason IN result.reasons:   // O(k)
      freq_map[reason] += 1               // O(1) hash lookup

  total_flagged ← len(flagged)

  FOR EACH (rule, count) IN freq_map:
    freq_map[rule].pct ← round(count / total_flagged × 100)

  RETURN sorted(freq_map, key=count, descending=True)

Algorithm C — Time-Series Bucketing (Monthly Trend)
Descriptive Analytics · config/views.py · lines 327–340
Time: O(n log n) 
// n = applications,  m = distinct months
// Space: O(m)
FUNCTION compute_monthly_trend(date_filter):
  monthly_qs ← Application.objects
    .filter(date_filter)
    .exclude(status="draft")
    .annotate(month=TruncMonth("created_at"))  // bucket by month
    .values("month")
    .annotate(count=Count("id"))                // count per bucket
    .order_by("month")                           // sort chronologically

  // Equivalent SQL produced by Django ORM:
  // SELECT DATE_TRUNC('month', created_at) AS month,
  //        COUNT(id) AS count
  // FROM programs_application
  // WHERE status != 'draft'
  // GROUP BY 1  ORDER BY 1

  max_count ← max(monthly_qs, key=count)
  FOR EACH row IN monthly_qs:
    row.pct ← round(row.count / max_count × 100) // normalize for chart

  RETURN monthly_qs
Algorithm D — Relative Frequency (Approval / Rejection Rates)
Descriptive Analytics · config/views.py · lines 344–362
Time: O(1) per metric 
// Relative frequency formula:  P̂(x) = f(x) / n
// where f(x) = count of outcome x,  n = total count
FUNCTION compute_program_stats(program, date_filter):
  base     ← Application.objects.filter(program=program)
  total    ← base.count()                           // n
  approved ← base.filter(status="approved").count()  // f(approved)
  rejected ← base.filter(status="rejected").count()  // f(rejected)
  pending  ← base.filter(status__in=["for_review"]).count()

  IF total > 0:
    approval_rate  ← round(approved  / total × 100)  // relative frequency %
    rejection_rate ← round(rejected  / total × 100)
    pending_rate   ← round(pending   / total × 100)

  RETURN { total, approved, rejected, pending,
           approval_rate, rejection_rate, pending_rate }
Section 5
Mathematical Formulas Used
Relative Frequency (Approval / Rejection Rate)
P̂(x) = f(x) / n × 100
f(x) = count of applications with outcome x
n = total submitted applications

e.g. 14 approved out of 50 → 14/50 × 100 = 28%
Monthly Bar Normalization
pctm = countm / max(count) × 100
countm = applications in month m
max(count) = peak month count

Scales all bars so the busiest month = 100% height, making the chart readable at any scale.
Rule Flag Rate (per rule)
flag_rater = f(r) / F × 100
f(r) = number of flagged results containing rule r in their reasons list
F = total flagged applications

Used in the hybrid output: "Income rule flagged 58% of flagged applicants."

Section 8
How to Test Descriptive Analytics

Testing method: Black-box output validation — seed a known dataset, then verify the system's computed outputs match manual calculations.

Step-by-Step Test Procedure

  1. Create N known applications with known statuses (e.g., 10 approved, 5 rejected, 5 pending)
  2. Open the Reports page and check: Total = 20, Approved = 10, Approval Rate = 50%
  3. Manually calculate: 10/20 × 100 = 50% — if the page shows 50%, Algorithm D is correct
  4. Create applications dated across multiple months; verify the monthly chart shows the correct bar heights for each month
  5. Submit an application that violates a rule; confirm the screening pass/flag counts update on the Reports page
  6. Check which rule name appears in the flag frequency section — it should match the rule you configured

What Constitutes a Passing Test

✓ System-computed approval rate matches approved ÷ total × 100 manually calculated from the database
✓ Monthly chart bar for each month equals the actual count of applications submitted in that month
✓ Flagged rule names on the Reports page match the violated rules in the applicant's ScreeningResult.reasons field
✓ Adding or removing an application updates all aggregated counts and percentages on the next page load
Section 9
Defense Questions — Prepared Answers
Q1: How do you test the descriptive analytics?
We test it through black-box output validation. We insert a known dataset — for example, 20 applications with 10 approved — then manually calculate what the approval rate should be: 10 ÷ 20 × 100 = 50%. We then open the Reports page and verify it shows 50%. If it does, the relative frequency formula is implemented correctly. We apply the same method to the monthly trend chart: applications created in January should produce a January bar, and its height should correspond to the correct count. The testing requires no specialized tool — only a known input and a verified expected output.
Q2: Where is descriptive analytics in the system?
The descriptive analytics layer lives in two files. The computation is in config/views.py inside the reports_view() function — it queries Application records, groups them by month using Django's TruncMonth, and computes counts and percentages for each program. The presentation layer is in templates/reports.html, which renders those computed values as bar charts and summary cards. Specifically, the formulas are on lines 327–392: Algorithm C (time-series bucketing) for the monthly trend and Algorithm D (relative frequency) for the approval rate, rejection rate, and pending rate per program.
Q3: What algorithm or formula does it use?
The system uses three algorithms. First, time-series bucketing (O(n log n)): Django's TruncMonth groups all applications by calendar month and COUNT aggregates each group — equivalent to a SQL GROUP BY DATE_TRUNC. Second, relative frequency (O(1) per metric): each status count is divided by the total and multiplied by 100, using the formula P̂(x) = f(x)/n × 100 — the standard descriptive statistics proportion formula. Third, hash map frequency counting (O(n×k)): this processes the output of the rule-based layer, counting how often each rule name appears in flagged screening results to identify which eligibility criteria most commonly rejects applicants. These three algorithms together constitute the descriptive analytics component.
Q4: How is it hybrid? Don't the two components work independently?
They work independently in terms of algorithmic logic, but they are coupled through data. The rule-based engine saves its output — a ScreeningResult record containing an outcome and a list of violated rule names — to the database. The descriptive layer then reads those ScreeningResult records as its input: it counts pass vs. flag outcomes and applies frequency analysis to the reasons list to show which rules are flagging the most applicants. The output of one algorithm is the input of the other's analysis. That pipeline, where a classification algorithm's output feeds a statistical aggregation algorithm, is precisely what defines a hybrid system.
