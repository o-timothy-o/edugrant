Component 1
Rule-Based Analytics
Decision Table Evaluation — O(r × a) — programs/services.py → run_rule_evaluation()
Evaluation Method

Domain Expert Validation. All 37 submitted applications were run through the rule engine. Each output (Pass / Flag) was verified against expected outcomes by the system author, who independently assessed each application against the program's eligibility rules. This constitutes a structured test-case evaluation using actual application data.

Algorithm — Decision Table Evaluation · O(r × a)

For each submitted application, the system retrieves all ProgramRule records for the target program. Each rule defines three things: a field (e.g., monthly_income), a condition (e.g., must not exceed), and a threshold value (e.g., ₱25,000). The engine evaluates every rule against the applicant's profile data in sequence. If all rules pass → outcome = "Pass". If any rule fails → outcome = "Flag" and the violated rule name is appended to reasons[]. Time complexity is O(r × a): r rules evaluated per application, across a total applications.

Feeds Into

The ScreeningResult record (outcome + reasons list) is stored per application and displayed on the Application Review page. The reasons list feeds directly into the Hybrid Analytics layer — it is compared against the admin's rejection reasons to compute the concordance rate. It also feeds into the Descriptive Analytics layer, where screening pass/flag counts are aggregated by program and by month.

// Accuracy — proportion of all correct predictions
Accuracy = (TP + TN) / (TP + TN + FP + FN)
         = (5 + 32) / (5 + 32 + 0 + 0) = 37/37 = 1.00 (100%)

// Precision — of all flagged, how many were truly ineligible
Precision = TP / (TP + FP) = 5 / (5 + 0) = 1.00 (100%)

// Recall — of all truly ineligible, how many were caught
Recall = TP / (TP + FN) = 5 / (5 + 0) = 1.00 (100%)

// F1-Score — harmonic mean of Precision and Recall
F1 = 2 × (Precision × Recall) / (Precision + Recall)
    = 2 × (1.00 × 1.00) / (1.00 + 1.00) = 1.00 (100%)

Component 2
Descriptive Analytics
Time-Series Bucketing · Hash Map Frequency Count · Relative Frequency — config/views.py → reports_view()
Evaluation Method

Benchmark Cross-Verification (Excel/Google Sheets). The system's computed statistics were independently recomputed from the raw CSV export (/reports/export/applications/) using COUNTIF and COUNTIFS formulas. The metric used is MAPE (Mean Absolute Percentage Error) — a value of 0% confirms the system's calculations are deterministically correct.

Algorithms — Three Sub-Algorithms

① Time-Series Bucketing — O(n log n): Groups all submitted applications by calendar month using Django's TruncMonth() database function, then counts records per bucket with Count(). The O(n log n) complexity comes from the sort applied to the month timestamps. Produces the Applications Over Time bar chart.

② Hash Map Frequency Count — O(n × k): Builds a frequency map keyed by status or program. Django's values() + annotate(count=Count()) executes a SQL GROUP BY — equivalent to a hash map keyed by category. n = total applications, k = number of distinct categories (status values or programs). Produces the stat cards (Total Submitted, Approved, Rejected, Pending) and the per-program breakdown bars.

③ Relative Frequency — O(1): Computes P̂(x) = f(x) / n × 100 for each status category. Given the frequency counts from ②, each rate is a single division — constant time per metric. Produces approval rate, rejection rate, and pending rate percentages.

Feeds Into

The Reports dashboard — stat cards, Applications Over Time chart, and per-program breakdown. The screening outcome data produced by the rule engine (ScreeningResult records) is also aggregated here using Hash Map Frequency Count — pass/flag counts by program and by month are displayed on the Screening Analytics sub-page. This is the Hybrid connection: rule-based output flows into the descriptive aggregation layer, making the two components interdependent.

Component 3
Diagnostic Analytics
Categorical Frequency Distribution with Pareto Ordering — O(n) — config/views.py → rejection_reasons_view()
Evaluation Method

Benchmark Cross-Verification (Excel/Google Sheets). The rejection reason frequencies shown on the Rejection Reasons page were independently recomputed from the CSV export. For multi-reason rejections (JSONField list), each reason was counted separately. MAPE is used as the accuracy metric.

Algorithm — Categorical Frequency Distribution with Pareto Ordering · O(n)

Iterates through all rejected applications once — O(n). For each application, it expands the rejection_reason JSON array field, since a single application may carry multiple reasons. Each reason key increments a running counter. After all applications are processed, the counter is sorted in descending frequency order (Pareto principle: the most common cause ranked first). The sorted result is rendered as a horizontal bar chart on the Rejection Reasons page, making the dominant cause immediately visible.

Feeds Into

The Rejection Reasons page (Pareto bar chart and ranked data table). The stored rejection reasons also feed into the Hybrid Analytics concordance analysis — for each rejected application, the admin's rejection_reason[] is paired with the rule engine's ScreeningResult.reasons[] to measure whether the two layers agree on why an application was rejected.

Component 4
Hybrid Analytics
Rule-Diagnostic Concordance Analysis — coupling of Rule-Based and Diagnostic layers
Evaluation Method

Rule-Diagnostic Concordance Analysis. For each of the 11 rejected applications, the rule engine's flag reason(s) were compared against the admin's selected rejection reason(s). A match is recorded when the admin's rejection reason directly corresponds to the rule engine's flagged criterion. This validates the hybrid pipeline coupling: rule-based output (ScreeningResult.reasons) feeding into the diagnostic layer.

Pipeline Architecture — How the Hybrid Layer Works

The hybrid analytics layer is not a standalone algorithm — it is a pipeline that couples the Rule-Based and Diagnostic components. The connection flows in two directions:

Rule → Descriptive: Every time the rule engine evaluates an application, it writes a ScreeningResult record (outcome + reasons list). The Descriptive Analytics layer reads these records and aggregates them using Hash Map Frequency Count — producing screening pass/flag counts by program and by month. Rule-based output is therefore a direct data source for descriptive statistics.

Rule → Diagnostic (Concordance): When an admin rejects an application, they select rejection reasons stored in Application.rejection_reason[]. The concordance analysis pairs each rejected application's ScreeningResult.reasons[] against its rejection_reason[]. A high rule-guided concordance rate confirms the two layers of the hybrid system produce aligned outputs — validating that the rule engine's automated screening is consistent with human judgment.

Interpretation

The concordance analysis reveals two distinct categories of rejection:

ℹ️

Rejection #7 (Partial): The rule engine correctly flagged an existing/prior scholarship conflict. However, "Existing Scholarship" is not currently a selectable rejection reason in the admin interface, so the admin defaulted to "Other." This is a gap in the rejection reason dropdown, not an algorithmic error.

✅

83.3% Rule-Guided Concordance demonstrates that when the rule engine flags an application, the admin's subsequent rejection decision directly aligns with the flagged criteria in 5 out of 6 cases. The 5 admin-discretion rejections highlight the value of the hybrid architecture: rule-based screening handles quantifiable criteria automatically, while the admin layer captures qualitative factors that rules alone cannot detect.
